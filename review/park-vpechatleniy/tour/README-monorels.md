## Что подтверждают эти отчёты

Оба текущих отчёта описывают **численную геометрию и CPU-поведение**. Для сценария движения применялся настоящий модуль runtime с геометрическим заменителем, имеющим проверенные габариты вагона. Это не браузерный/WebGL-тест финального GLB. Совместная проверка сцены использовала реальные зарегистрированные collision parts и исходные/preview-модели для уточнения потенциальных контактов.

Проверка выполнена дискретно с шагом до 0,05 м и запасом 0,10 м на гранях вагона. Измеренный максимальный пространственный шаг центра равен 0,050166478 м, изменение полного поворота между соседними позами — 0,383059°. Оценка перемещения поверхности между ближайшей контрольной позой и промежуточным положением составляет около 0,047986 м. Это численная оценка покрытия; формальное доказательство непрерывного отсутствия контактов не заявлено.

Исходный CAD не изменён; его SHA256 в обоих итоговых отчётах:

#### Модуль и интеграция

`tram-system.js` — ES-модуль для Three.js r180. `createTramSystem({scene, modelUrl, loader, routeConfig, onState, supportFloorHeight})` получает существующий GLTFLoader с MeshoptDecoder. Viewer передаёт экспорт `MONORAIL_ROUTE_CONFIG`. Оставшийся `DEFAULT_ROUTE_CONFIG` относится к совместимому прежнему конструктору замкнутой петли и не является текущей конфигурацией viewer.

Кроме управления движением, камерами сопровождения и видом из вагона, модуль предоставляет `getStationPose()`, `getSupportRecords()`, `getCollisionObstacles()`. В состоянии отражаются `routeMode`, направление, остановка, интервал и `boardingVehicle`. Собственный DOM и цикл кадров модуль не создаёт. При ошибке загрузки настоящего GLB подменные вагоны в сцену не добавляются.
